# Build: College Football Player Value & Game Prediction System

You're building a two-stage modeling system on top of the CollegeFootballData (CFBD) API. Stage 1 estimates a value for every player from play-level data using a hierarchical Bayesian model. Stage 2 aggregates those values into team strength and predicts game margins and win probabilities. Read this entire document before writing code, then start with Phase 0.

## How to work

- Work in phases. At the end of each phase, stop, summarize what you built and what you found, list open questions, and wait for my approval before starting the next phase.
- Every command that calls the CFBD API is **dry-run by default**: it prints the planned requests and the estimated call count, then exits. It only hits the network with `--execute`. The API has a call budget, so this matters.
- Once something works, prefer small, targeted changes over rewrites.
- When the data contradicts an assumption in this document, trust the data, tell me, and propose an adjustment. Several details below were read from the client library's spec and have not been confirmed against live responses.
- Ask before adding dependencies outside the stack listed below.

## Environment

- Python 3.11+, managed with `pyproject.toml` and a virtual environment.
- Secrets: `CFB_APIKEY` lives in a `.env` file loaded with `python-dotenv`. Never log or commit the key. Add `.env` and `data/` to `.gitignore`.

**Stack:** httpx, tenacity, polars + pyarrow, duckdb, numpyro + jax, arviz, lightgbm, scikit-learn, rapidfuzz, python-dotenv, pytest.

## The CFBD client library

The `cfbd` Python client (v5.32.1, generated by OpenAPI Generator 7.12) is vendored at `vendor/cfbd-python/`. Use it as the **schema and parameter reference**: endpoint docs are in `vendor/cfbd-python/docs/*Api.md`, and response models are in `vendor/cfbd-python/cfbd/models/`.

Do **not** install it as a project dependency. It pins `pydantic<2`, which conflicts with modern packages. It also validates every row with strict types, so it can fail on an unexpected null. Call the REST API directly with httpx instead: base URL `https://api.collegefootballdata.com`, header `Authorization: Bearer <key>`.

Facts already established from the spec (verify them during the Phase 1 probe):

- The API has **no snap count, participation, depth chart, or injury data anywhere**. Only players involved in a play are named.
- `/plays` includes `ppa` (CFBD's EPA) and game state but no athlete IDs. It requires `year` and `week`.
- `/passing/plays` and `/rushing/plays` come pre-parsed with `passer_id`, `target_id`, `rusher_id`, air yards, YAC, depth/direction, `ppa`, and `success`. They also include the quality fields `parse_status` and `attribution_status`. `year` is required.
- `/plays/stats` maps `play_id` → `athlete_id` + `stat_type` for every credited player, including defenders. It is **capped at 2,000 rows per call**, so pull it per `game_id`.
- `/player/portal` (transfers) has **no athlete ID**. It only has first and last name, position, origin, destination, and season.
- `/roster` defaults `year` to 2025. **Always pass `year` explicitly.**
- `roster.recruit_ids` and `recruiting/players.athlete_id` link players to recruiting records.
- `/draft/picks` includes `college_athlete_id` and `pre_draft_grade`.
- `/games` includes pregame Elo for both teams. `/venues` has lat/long, elevation, timezone, dome, and grass.
- `/games/weather` and `/games/{id}/preview/adjusted` require a Patreon tier. Weather is optional, behind a flag.
- `GET /info` returns the account's Patreon level and remaining calls.

## Phase 3: Stage 1, the player value model (NumPyro)

**Target:** play-level `ppa`. **Likelihood:** Student-t, because EPA has heavy tails from scores and turnovers.

**Play equations** (higher = better for the offense):
- Pass play: `μ = context·β + θ_passer + θ_target + O_off_unit − D_def_unit + (credited defenders)`
- Rush play: `μ = context·β + θ_rusher + O_off_unit − D_def_unit + (credited defenders)`
- `context` covers down, distance bucket, yards-to-goal bucket, and home/neutral.

**Unit effects:** `O` and `D` are team-season effects, hierarchical over conference. They absorb offensive linemen, scheme, and uncredited defenders, none of which this data can see individually. Opponent adjustment comes through the defensive unit term.

**Player effects** are role-specific in v1: passing, rushing, receiving, and defensive effects are separate parameters, so a QB has both a passing and a rushing effect. Each one decomposes as:

`θ[p,s,g] = α_position + c[p] + s[p,s] + g[p,s,g]`

- `c[p]` (career effect) ~ Normal(Xγ, τ_c). X contains recruiting rating and stars, height and weight standardized within position, a missing-recruit indicator, and a transfer indicator. This is how qualitative and pre-college information enters the model: as an informed prior that on-field data then updates.
- `s[p,s]` (season effect) follows a random walk across seasons: `s[p,s] = s[p,s−1] + ε`, with ε ~ Normal(0, τ_s). Give a player's first season its own prior.
- `g[p,s,g]` (game effect) ~ Normal(0, τ_g) with a tight prior. Start with iid game effects. Upgrade to a within-season random walk only if held-out log-likelihood improves.

**Defensive credit** is the hardest design choice here, because tackle credits are selection-biased: a tackle after a 20-yard gain isn't a positive play. Before implementing, propose two or three options with their trade-offs and let me choose. Candidates include stat-type-specific effects, modeling only negative-outcome stats (sacks, TFL, PBU, INT) individually, or a separate defender model.

**Out of scope for v1:** kickers and punters (use `/wepa/players/kicking` PAAR as-is if needed) and individual offensive linemen.

**Inference**
- First validate on one season with NUTS, reporting R-hat, ESS, and divergences.
- Then fit at scale with SVI (start with AutoNormal, then try AutoLowRankMultivariateNormal) and show that SVI and NUTS agree on the validation season.
- **As-of fitting is mandatory.** The ratings used to predict a week-w game come from a fit on data through week w−1 only. Refit weekly with SVI, warm-started from the previous week's parameters. The refit cadence is configurable in case weekly is too slow.

**Output:** a `player_values` table keyed by (athlete_id, season, through_week, role), with posterior mean, posterior sd, play count, and value expressed as EPA per play above position average.

**Validation**
- Held-out play log-likelihood versus a context-only baseline.
- Correlation with CFBD's `/ppa/players/*` and `/wepa/players/*` by position. List the largest disagreements and explain them.
- Draft check: within position, do higher career effects predict earlier draft selection? Draft data is for validation only and is never a feature.

**Stop.**

## Phase 4: Stage 2, the game model

Build the baselines first (4a), then the model (4b), so the bar is set before anything gets tuned.

**4a: Baselines.** Pregame Elo from `/games`, `/metrics/wp/pregame`, and the opening and closing spreads from `/lines`. Convert each to a home margin and a win probability.

**4b: Features**, all computed as of the prior week:
- **Projected usage.** No depth chart or injury data exists, so project each player's involvement share (dropbacks, carries, targets, defensive credits) from their recent games, over a configurable window. Flag high-usage players with zero involvement in their most recent game as possibly unavailable.
- **Team strength.** Usage-weighted sums of player posterior means and variances by unit (passing, rushing, receiving, defense), plus the O/D unit effects. The QB is its own feature.
- **Situational.** Home/neutral, travel distance, time-zone change, elevation, rest days, and a coaching-change flag. Travel and time zone come from venue coordinates and timezones; derive each team's home venue from its home games.
- **Early-season priors** (weeks 0–3): `/talent`, `/player/returning`, and prior-season final ratings.

**Model:** LightGBM regression on home point margin, plus a ridge regression as a sanity comparison. Convert margin to win probability with a calibrated mapping fit on validation residuals.

**Stop.**

## Leakage rules (enforce in code and tests)

- Every feature row carries an `as_of` (season, week). A pytest test asserts that no feature uses data from a game on or after the target game's date.
- Season-level endpoints (`/ratings/*`, `/ppa/players/season`, `/wepa/*`, `/player/usage`) return full-season values, so never use them as same-season features. Prior-season values are fine as priors.
- Betting lines are benchmarks only, never features. Otherwise the model just learns the spread.
- Draft data is validation only.

## Phase 5: Evaluation

**Rolling-origin backtest:** for each season and week, train on all prior seasons plus the current season through week w−1, then predict week w.

**Reporting:**
- Break results down by season and by week bucket: weeks 0–3, 4–8, 9+, and postseason.
- Metrics: MAE on margin, log loss, Brier score, calibration curve, straight-up accuracy, and against-the-spread record versus both opening and closing lines.
- Show every metric alongside all baselines.
- Include an ablation of the full model with and without the player-value features, to show what stage 1 actually adds.

Write reports to `reports/` as markdown with charts.

**Stop.**
